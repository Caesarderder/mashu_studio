# 需求先检索，经验再沉淀

## 核心规则：先找到已有方法和事实，再开发

用户提出需求后，先判断任务所属职能与当前项目，读取相关skill入口和docs index。沿地图快速搜索同类需求、已确认决定、规范、工作流、配置源、实现/资产落点与验证记录；可以用稳定ID、功能名及旧别名检索。取得本轮必要信息即停止扩读，不要求读完整地图或全部skills。

找到流程就复用；记录有版本/状态冲突时核对当前源码与最新用户决定，不能把旧验收当当前事实。没有相关记录时明确缺口，进行最小必要发现后实现，不为了等文档而停工。明显单行修正或用户明确指定跳过时按任务精简。

开工前简述需求、采用的skill/docs路线、真实编辑源与验证方式。已有授权持续有效，不把“先读文档”变成反复询问许可。完成后将实际变更和证据回写原位置。

## 识别值得复用的流程

出现可重复步骤、复杂工具/格式转换、同类资产量产、跨岗位交接、经常发生的验证/恢复操作时，判断是否值得整理为docs工作流。先搜索等价流程，优先更新原文。

未授权整理时，在当前任务交付中简短提醒用户：建议沉淀哪个流程、可复用在哪、建议放哪；询问是否整理，不因此中断已授权开发，也不提前写一堆无关文档。已有维护/整理授权或正在修订相关工作流时直接同步，不重复请求确认。

工作流写触发条件、输入/前置、实际配置与工具入口、关键步骤、输出/验证、已知限制、回写位置；记录写本次版本、操作、结果和证据。索引只保留路由，不积累逐轮聊天。

## 从反复要求到通用skill

用户多次强调的事项先识别根因和适用边界，不因重复就升级为所有项目的硬约束：

- 只影响本游戏的规则、数值、风格、端口、身份、偏好与认可 → 本项目决定/配置/工作流。
- 已验证、可跨项目复用的制作方法、质量标准、常见失误和检查方法 → 对应通用skill或其专项参考。
- 尚未验证或只发生一次的猜测 → 本轮记录/候选建议，明确证据缺口。

提出skill优化时说明原有缺口、适用场景与依据；授权内更新已知源码，再合并并同步副本，保护本地分歧。去除具体项目身份与数值，不建立同名重复技能，不把同一句规则复制到每个模块。更新之后做对应格式、链接和必要脚本检查。
